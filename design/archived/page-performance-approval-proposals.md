## 使用规则

- 每条提案独立审批。
- 审批状态仅表示“方向是否通过”，不表示“已经实现”。
- 若提案被通过，后续再拆实现任务和代码改造步骤。

## 提案明细

### PA-001 固定五轨道页面骨架

- 状态: `approved`
- 目标:
  消除 toast、search、footer 变化导致的主内容区高度跳变。
- 方案:
  页面固定为五条轨道:
  1. `Header Rail`
  2. `Message Rail`
  3. `Query Rail`
  4. `Panel Rail`
  5. `Footer Rail`
- 推荐:
  通过。先稳定骨架，再讨论各页面内部排版。
- 推荐理由:
  1. 当前最直观的问题是 panel 高度抖动。
  2. 这个问题不先解决，后续任何页面优化都会被 layout jitter 抵消。
  3. 该方案对后续 BR-002/003/004/005 都是共同基础。
- 影响:
  1. `RenderApp()` 需要改成固定轨道计算。
  2. 顶部和底部不再按自然高度反推 panel 高度。
  3. 小终端下需要设计降级策略。
- 风险:
  1. 若轨道高度定得过死，小终端会更紧张。
  2. 若不配合后续 Query / Message 拆分，收益不完整。
- 审批点:
  是否同意将“固定轨道骨架”设为页面优化第一优先级。
- 审批结果:
  通过，并明确为后续页面渲染体系第一优先级。

### PA-002 Query Rail / Message Rail 统一化

- 状态: `approved`
- 目标:
  让搜索、过滤、命令输入与轻量通知进入统一轨道，而不是随页面插入。
- 方案:
  1. `Message Rail` 统一承接:
     - Toast
     - Filter 第一次 `Esc` 提示
     - Search 命中提示
     - 轻量成功/失败提示
  2. `Query Rail` 统一承接:
     - `Filter`
     - `Search`
     - `Command`
- 推荐:
  通过。
- 推荐理由:
  1. 能直接减少布局跳变。
  2. 让 BR-004 的 Filter / Search 状态机有固定落点。
  3. 为 BR-005 的通知系统提供稳定 UI 投影位置。
- 影响:
  1. `renderSearchBar()` 需要从“插入 panel 上方”改为“固定轨道渲染”。
  2. 通知逻辑需要逐步从分散提示迁到 message rail。
- 风险:
  1. 若 rail 内容表达不清，小终端可读性会下降。
- 审批点:
  是否同意将 Query / Message 作为独立固定轨道，而不是继续作为临时插入块。
- 审批结果:
  通过，且需与 `BR-004`、`BR-005` 的既有模式和通知方案协同。

### PA-003 页面模板统一为 5 类

- 状态: `approved`
- 目标:
  用统一模板承接同类页面，避免每页各自生长布局语言。
- 方案:
  页面统一抽象为:
  1. `List Page`
  2. `Split Page`
  3. `Detail Page`
  4. `Log Page`
  5. `Help Page`
- 推荐:
  通过。
- 推荐理由:
  1. 当前容器/镜像/卷/网络本质上都是列表页。
  2. Compose 与 image subview 已经证明 split page 是有效模式。
  3. Detail / Log / Help 的信息组织差异足够大，单独成型更合理。
- 影响:
  1. 后续页面优化优先修改模板，不直接在单页打补丁。
  2. 新需求接入时先判断模板归属，再决定页面细节。
- 风险:
  1. 第一阶段会有“旧页面实现 + 新模板抽象”并存期。
- 审批点:
  是否同意未来页面优化和新增页面都必须先归入模板类型。
- 审批结果:
  通过，后续页面优化与新增页面均需先归类到模板体系。

### PA-004 Footer / Help / 标题摘要统一投影层

- 状态: `approved`
- 目标:
  统一动作、状态、标题摘要的投影来源，避免 Help、Footer、标题各写一套真相。
- 方案:
  1. 动作事实由动作系统统一提供
  2. Footer / Help 从同一动作投影层派生
  3. Panel Title / Summary / Selection Preview 走统一 projector
- 推荐:
  通过。
- 推荐理由:
  1. 这能直接解决 BR-003 的信息源漂移问题。
  2. 页面优化如果不接统一投影层，只会把旧问题换个位置重复一遍。
- 影响:
  1. Footer 与 Help 后续都要重构数据源。
  2. 页面标题摘要应与具体 view model 解耦。
- 风险:
  1. 与 BR-002 有依赖关系，不能完全独立推进。
- 审批点:
  是否同意将“统一投影层”作为页面说明系统的唯一方向。
- 审批结果:
  通过，并明确要求与 `BR-002 / BR-003` 既有动作与展示收敛方案共用同一来源。

### PA-005 表格布局与列宽缓存

- 状态: `approved`
- 目标:
  降低 `RenderTable()` 高频路径中的重复宽度计算和 `VisibleLen()` 成本。
- 方案:
  1. 新增 `TableLayoutCache`
  2. 先缓存:
     - profile
     - columns schema
     - container width
     - resolved headers
     - column widths
  3. 第一阶段不缓存整表字符串
- 推荐:
  分阶段通过。
- 推荐理由:
  1. 表格是最常见页面，缓存收益明确。
  2. 但过早缓存整表输出会显著抬高复杂度。
  3. 先做“宽度缓存”比“全量 render cache”更稳。
- 影响:
  1. `RenderTable()` 需要引入 layout cache 接口。
  2. 列宽重算触发条件需要明确定义。
- 风险:
  1. 若 cache key 设计不准，容易出现宽度过期或显示错误。
- 审批点:
  是否同意“只缓存宽度与表头，不缓存整表字符串”作为第一阶段边界。
- 审批结果:
  通过，且限定第一阶段只缓存宽度与表头。

### PA-006 日志页 viewport 优化

- 状态: `approved`
- 目标:
  修正日志页宽度计算和高频渲染成本，让其符合 `Search` 模式语义。
- 方案:
  1. wrap 宽度改为真实 panel body width
  2. 仅对当前 viewport 做 wrap 和高亮
  3. 将搜索反馈与 viewport 状态分离
- 推荐:
  通过。
- 推荐理由:
  1. 当前 `m.Width - 10` 的宽度来源不正确。
  2. 日志页属于高密度、高滚动频率页面，性能收益直接。
  3. 与 BR-004 的 Search 模式边界一致。
- 影响:
  1. 日志页 renderer 需要接收更精确的 content width。
  2. Search 状态提示后续应接 message rail。
- 风险:
  1. 若 wrap 与 highlight 逻辑耦合不拆，会继续影响维护性。
- 审批点:
  是否同意将日志页单列为独立优化对象，而不是顺带一起修。
- 审批结果:
  通过，日志页作为独立页面类型单独优化。

### PA-007 详情页结构化 section 渲染

- 状态: `approved`
- 目标:
  让详情页从“文本驱动布局”转为“section model 驱动布局”。
- 方案:
  1. 优先对镜像详情页接入 typed section model
  2. Detail Page 模板统一 section 标题、subtitle、empty state
  3. `History`、`Config`、`Storage` 等高密度区块允许独立 renderer
- 推荐:
  通过。
- 推荐理由:
  1. 这是 BR-001 的直接延伸。
  2. 不先做 section 化，详情页页面优化没有稳定结构基础。
- 影响:
  1. 详情页 renderer 需要脱离文本反解析路径。
  2. 后续其他资源详情页可以复用相同页面模板。
- 风险:
  1. 第一阶段只适合先落镜像详情，不宜一次收全资源。
- 审批点:
  是否同意将详情页结构化 section 作为 detail page 优化的唯一方向。
- 审批结果:
  通过，且第一阶段继续优先落镜像详情。

### PA-008 性能优化按高频路径优先级推进

- 状态: `approved`
- 目标:
  控制优化范围，避免一开始就做大而全的缓存系统。
- 方案:
  性能优化推进顺序固定为:
  1. Layout jitter 消除
  2. Query / Message rail 固定化
  3. 日志页 viewport 优化
  4. 表格列宽缓存
  5. 字符串可见宽度缓存
  6. 更深层 render model 分层
- 推荐:
  通过。
- 推荐理由:
  1. 先做高收益、低风险项。
  2. 避免过早引入大范围 cache invalidation 复杂度。
- 影响:
  1. 第一阶段不会立即追求“极限性能”。
  2. 更关注可持续结构与主要卡点。
- 风险:
  1. 若用户预期是立即追求极限性能，需要提前对齐边界。
- 审批点:
  是否同意按固定优先级推进，而不是并行铺开所有优化点。
- 审批结果:
  通过，并按既定优先级推进。
